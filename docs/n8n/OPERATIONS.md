## Schedule and ownership

The main schedule is `0 18 * * 1-5` in `Asia/Taipei`. A second schedule reconciles every ten minutes from 18:00 through 20:50 on weekdays. It uses the same stable date/request key and skips an already verified operation. The installed Schedule Trigger v1.4 accepts durable `misfirePolicy: coalesce`; bounded evening reconciliation also covers an omitted same-day dispatch.

Scheduled executions use the local Taipei date. A normal manual execution with no explicit date resolves the latest completed session from the independently fetched TWSE holiday calendar and the 13:30 Taipei close. Saturday October 3 resolves Friday October 2; before the close, the previous open session is selected. The resolver fails closed when crossing an unavailable calendar year. It never selects a stale website feed as the expected date. Actions independently verifies its official source watermark before financial supplement. ROC dates are converted to ISO dates, calendar year must match, and explicit opening events are distinguished from closures. Invalid, empty, unavailable, or mismatched-year calendars fail closed. Closed days produce a skip ledger and no Actions dispatch or Notion stock database. Historical recovery requires an explicit operator date and exact Actions request/run; the workflow never fabricates a market date from stale quote data.

Each writer claims `operations/days/YYYY-MM-DD.json` on the separate GitHub branch `n8n-state`. A new file is created without a SHA; an existing file is updated with its observed blob SHA. Conflicts abort the follower. Every checkpoint commit starts with `[CF-Pages-Skip]` so state writes do not trigger Cloudflare preview builds. Data Tables are an audit ledger, not a uniqueness or lock authority.

The instance enforces a 3600-second execution maximum. Each execution has a 59-minute writer deadline. A successor may take ownership only after that deadline plus 60 seconds, exceeding the configured 20-second HTTP Request duration. The native GitHub dispatch node exposes no per-request timeout option; its dispatch intent is saved before sending, and any unknown result is searched by exact request instead of resent. A gate after every Wait node prevents the old owner from starting another operation after its deadline. Scheduled recovery keeps the original absolute 19:30 Taipei operation cutoff; it does not start another 90-minute daily window. The target remains 18:45. A 65-minute Actions job can therefore be resumed by the 19:10 checkpoint using the persisted exact run ID, without dispatching again. Explicit manual resume is allowed after the scheduled cutoff with a fresh 90-minute operation window; its original scheduled cutoff and manual override timestamp remain in the audit state. It still cannot take a live lease.

A scheduled automatic screen may create one `:retry1` job only after exact run, job and artifact guards prove a source failure before publication. Each job may invoke the official-universe collector three times, with 15/30-second gaps. Six collector invocations across the original and retry are not an exact HTTP request count. A second failed job remains failed; recovery ticks adopt that saved request/run instead of dispatching more jobs. Explicit manual corrections are not eligible for this automatic retry. A new trading day requires a genuine source for that date; reusing an already verified same-date receipt helps a correction or repeat run, but cannot invent a receipt for a missing new session.

## Manual operation

Use **Run latest completed trading session** with the default **Operator inputs** to perform real work. The default blank date/request/run is resolved automatically; existing exact runs are resumed and completed operations are reported without repeating them. An automatic normal request adopts the same-day persisted corrected request after the active-owner guard; explicit differing requests remain strict. Legacy archive state is not adopted as a fresh screen. Only change fields for an explicit recovery, correction, legacy import, or diagnostic:

- `mode=screen`: default; resolves the latest completed session when the manual date is blank, then reads the durable day checkpoint and exact Actions request before dispatching any missing work. Existing runs resume with an audited manual window.
- `mode=diagnose`: explicit read-only Diagnostics branch; reads the official calendar and existing Notion database/data source. It records `diagnostics_only`, not screening/archive/deployment success.
- `mode=resume`: find the same exact request/run and resume artifact retrieval, Notion archive, or deployment verification. It never dispatches a missing run.
- `mode=legacy_archive`: authenticated immutable backfill for the six retained dates: 2026-09-08, 09-11, 09-18, 09-23, 09-24, and 10-01. It pins a verified main commit, reads index/month/revision evidence, verifies raw SHA-256 and date/run/revision, and archives the actual strategy union without screening. Original Actions/source lineage remains unknown; ingestion commit, legacy quality, original strategy rows, absent metric nulls, and revision hash remain explicit. Deployment checks the historical revision path.
- `mode=revision`: a correction with a new `request_id`. Existing stock revisions remain in the same child database; `Active Revision` moves only after the new selected union is verified.
- `market_date`: `YYYY-MM-DD`; normal manual blank selects the latest completed official session; scheduled blank uses today. Diagnostics use the requested/current date and never backfill.
- `request_id`: the exact dispatch correlation ID; blank uses `stockscreener:YYYYMMDD:v1`.
- `actions_run_id`: optional exact known run; the run title and source commit still must match.
- `preflight_retry_execution_id`: leave blank normally. A human-confirmed local native validation failure may be corrected only for the released exact failed execution owner, same date/request, no Actions ID and `dispatch_run_not_found`. The correction is audited, consumed and still searches exact runs before dispatch. Unknown transport failures do not clear intent automatically.
- `run_kind=manual`: retain for manual recovery. Scheduled inputs use `scheduled` and enforce the original 19:30 cutoff.

Restore `mode=screen` and blank operator date/request/run/preflight retry after an explicit recovery or import. Changing manual inputs does not change scheduled input values.

## Artifact and archive integrity

The GitHub run title must equal `Daily screening | REQUEST_ID | MARKET_DATE`; ambiguous matches fail closed. The artifact must be the single non-expired `screening-export` artifact from that exact run. Authenticated artifact lookup is followed by a signed download without forwarding GitHub credentials. The native Compression node extracts `screening-export.json` and `publication.json`.

Modern exports require complete nested `funnel.growthCoverageVersion=growth-coverage-v1` diagnostics, the canonical generic funnel version, nonnegative counts, exact exclusive terminal fields, and a common-share denominator equal to `funnel.universe - funnel.instrumentExcluded`. Valuation completeness cannot exceed input completeness; missing reasons must be unique with positive counts. Evaluation state and growth selected count must match the dispositions and strategy list. Missing inputs remain distinct from true zero results. Legacy imports use their separate immutable-evidence adapter.

The workflow hashes the exact UTF-8 preimage from the export's final `payloadHash` suffix, avoiding JavaScript/Python float reserialization differences. It verifies schema, date, request ID, Actions run ID, source commit, publication lineage, unique strategy ranks/codes, and the deduplicated selected-stock union. Named publication nodes then retrieve the exact immutable export at `publication.publishedGitCommit` through the existing GitHub credential and verify that commit is identical to or an ancestor of main before Notion writes. It rejects stale-universe exports. A valid empty union creates a complete empty child database; failed screening creates daily failure metadata and no child database or fabricated zero result.

The root Notion database is `3ed6fb57-ff38-8032-97cc-f017b6104300`; its data source is `3ed6fb57-ff38-803d-815a-000b148c6b6e`, and its title property is `名稱`. The HTTP nodes pin `Notion-Version: 2025-09-03` and disable header lowercasing: otherwise the existing credential's legacy-version fallback overrides the intended API version.

Stock codes use rich text and retain leading zeroes. Each stock row stores strategy tags, strategy ranks, numeric metrics, the complete metric JSON, provenance, formula/financial evidence, revision, payload hash, and the stable `Row Key=PAYLOAD_HASH:CODE`. Same-payload retries query existing keys before creating. Ambiguous create responses return to a read operation. Proven identical duplicate stock rows can be archived deterministically while preserving the oldest row; unrelated records and prior revisions are preserved. Parent block lists and stock queries are paginated.

All Notion requests are spaced at least 500 ms apart. HTTP 429 responses respect `Retry-After`, with a bounded retry count. Write nodes do not use blanket native retry settings. CAS checkpoints persist exact Actions/artifact/run IDs and discovered Notion IDs. Immutable artifact bytes are retrieved again during recovery rather than copied into the state ledger. Signed download URLs remain transient: success/error execution payload saving, manual execution saving, and execution-progress saving are disabled. The durable state and ledger exclude operation URLs and stock payloads. The live site host is pinned to `stockscreener.andyshih.uk`; operator Actions IDs must contain decimal digits only.

A dispatch whose response was ambiguous is searched by the exact request title and is never blindly sent again.
